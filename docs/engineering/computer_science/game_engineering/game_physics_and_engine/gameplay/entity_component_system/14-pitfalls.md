# Pitfalls

    Over-splitting components. Splitting Position into PositionX, PositionY, PositionZ (one component per field) is the most vectorization-friendly layout, but it turns one column into three: three streams for every loop that reads a position, three copies on every structural change, and three entries in every query. Most systems read all three fields together, so they pay for the split without collecting its benefit. Split only when profiling shows a hot system that reads one field and ignores the others.
    Archetype explosion. If entities carry many optional components and the combinations are diverse, the archetype count grows combinatorially: 20 optional components allow up to 2^20 archetypes. Many small archetypes mean short tables, more query matching, and more migrations. When the count keeps climbing, consider whether some of those "components" should be fields inside a larger component, or, in engines that allow it, move the frequently toggled ones to sparse-set storage.
    Structural change storms. A system that adds and removes components every frame (toggling a buff on and off) moves entities between archetypes every tick. Use a boolean field inside the component instead of adding/removing the component, or use command buffers to batch the changes.
    Dangling entity references. A component stores the ID of another entity, and that entity is destroyed, leaving the reference dangling. Generational indices detect this at resolve time, but the system must handle the failure case (skip, remove the component, spawn a replacement).
    System ordering bugs. System A writes a value that system B reads. Access analysis stops them from running at the same time, but it does not choose which runs first: with no declared order, a conflicting pair may run in either order, and Bevy calls that an ambiguity[31]. If B must see this frame's value, declare the order (.after(system_a) in Bevy).
