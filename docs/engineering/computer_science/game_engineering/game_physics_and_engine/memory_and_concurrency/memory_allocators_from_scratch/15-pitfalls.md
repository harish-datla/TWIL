# Pitfalls


The code on this page is deliberately small. These are the production problems it's too small to show.

    Alignment is not optional. SSE types want 16-byte alignment, AVX 32, and cache-line-sized data 64. GPU APIs add their own rules (D3D12 wants 256 bytes for constant-buffer data and 64 KB for most placed resources). An allocator that hands back under-aligned pointers will fault on aligned SIMD loads, the vector loads that require an aligned address (MOVAPS, VMOVDQA), fault on some older ARM cores' scalar accesses, and pay for a split access whenever a load straddles two cache lines, even where the hardware tolerates misalignment. Always take the requested alignment as a parameter and round the head up before returning.
    Debug allocators are not free. Pattern-fill on alloc and free, guard pages (inaccessible pages next to each allocation, so an overrun faults at once), leak tracking, and stack-trace capture can multiply allocation cost many times over; a stack-trace capture alone costs on the order of microseconds per call, and a guard page costs at least one page of address space per allocation. Unreal keeps leak tracking in a separate wrapper around the real allocator, switched on with MALLOC_LEAKDETECTION, rather than in the allocator itself; keep it out of shipping builds.
    Thread-local stack allocators break when jobs migrate. A job that saves a marker in thread A's arena, yields, and resumes on thread B (fibers, which a job system can suspend on one thread and resume on another, or work-stealing schedulers, where idle workers take jobs from busy ones) will later pop thread B's arena to a marker that belongs to A, freeing B's live allocations and leaking A's. Either attach the arena to the job rather than the thread, or free by lifetime instead of by scope: Naughty Dog's tagged heap gives each worker thread its own block but frees every block with a given tag at once, so a job that moves mid-frame just keeps allocating on its new thread[24]. The job-systems tutorial covers the work-stealing side.
    Use-after-free on a pool slot reads the free-list link. A freed slot's first bytes hold the index of the next free slot, so a stale read returns a plausible small integer instead of crashing, and a stale write corrupts the free list. Debug builds commonly fill the rest of a freed slot with a poison pattern (MSVC's debug heap uses 0xDD for freed memory) so a use-after-free shows up as an obviously wrong value; shipping builds skip the fill.
    Generational handles don't survive a save and load. After load, every entity gets whatever slot index and generation the fresh table hands out, so saved handles point at the wrong slots or fail validation. Serialize a stable ID (entity name, GUID) and translate it back to a handle at load time. Network replication has the same problem for the same reason.
    Cross-allocator frees corrupt the heap. A pointer from FMemStack passed to FMalloc::Free hands the general-purpose allocator a block it never issued, and the damage usually surfaces later, somewhere else. Every allocation must go back to the allocator that made it. One common defense is to keep pointers from special-purpose allocators out of APIs that might free them, so call sites hold the allocator or a scope object rather than an owning raw pointer.
    Buddy rounding can erase the gains of a slab above it. A 65-byte request to a buddy that rounds to 128 wastes 49% of the block. If request sizes don't cluster at powers of two, put pools or slabs of the actual object sizes on top of the buddy and give the buddy only large, power-of-two-friendly requests.
