# Bidirectional search

A path query between two points far apart explores a huge region around the start before it gets near the goal. Pohl's observation[15]: if a uniform-branching graph has branching factor b and the goal is at depth d, a single-direction BFS explores ~bd vertices to find it. Two BFS frontiers (one from the source, one from the goal, alternating expansion) meet in the middle after expanding ~2 · bd/2. The branching factor still applies, but the exponent halves. On a graph with b = 10 and d = 12, the single-direction count is 1012; the bidirectional count is 2 · 106. That gain does not carry over automatically to bidirectional A*. A good heuristic already keeps a one-way search narrow, and for decades bidirectional heuristic search did worse than plain A* in practice; Kaindl and Kainz showed that the popular explanation, frontiers passing each other without meeting, was wrong, and gave bidirectional variants that beat one-way search on some hard problems[33].

The catch is termination. The frontiers must exchange visited sets, and the meeting point isn't necessarily the first vertex one search reaches that the other has already seen; the shortest path runs through the vertex that minimizes distfwd(v) + distback(v). Keep the best such sum found so far and stop only when the two frontiers' smallest keys prove nothing cheaper can still appear (for bidirectional Dijkstra, when the two minimum queue keys add up to at least that best sum). Stop at the first meeting and the path you return can be longer than the shortest one.
