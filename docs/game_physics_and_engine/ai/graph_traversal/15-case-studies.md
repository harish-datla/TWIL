# Case studies

Five places in shipping engines where these walks run every frame or every build.
1 · The render-graph compile

Render-graph systems (Frostbite's FrameGraph[27], Unreal's RDG, the RenderGraph in Unity's Scriptable Render Pipeline) record each frame's rendering work as passes that declare the resources they read and write, then compile that record before executing it. O'Donnell's Frostbite talk splits compilation into culling and resource allocation, and both are graph walks, as is choosing the order:

    Culling drops every pass whose outputs nothing reads, directly or through later passes: reachability computed backwards from the frame's real outputs. Frostbite implements it as a reference-count flood fill. Every resource starts with a count of its readers and every pass with a count of the resources it writes; resources with no readers go on a stack, and popping one decrements its producer's count. A producer that reaches zero is culled, which in turn decrements the counts of the resources it reads.
    Resource lifetimes come from one walk over the surviving passes in execution order, recording each transient resource's first and last user. Frostbite acquires memory right before the first use and releases it after the last, so two render targets whose lifetimes don't overlap can share the same physical allocation.
    Ordering must respect every read-after-write dependency, which makes it a topological sort (§8). When a pass can only read resources that earlier-declared passes produced, the declaration order already is one. Render graphs that reorder passes to overlap GPU work sort explicitly: Granite's walks back from the backbuffer recursively, pushing every pass that writes a resource an already-listed pass reads, then reverses the list and prunes duplicates[35].

A graph built so that passes only read what earlier passes produced cannot express a cycle. One assembled from arbitrary dependency edges needs the back-edge check from §5 to reject one.
2 · F.E.A.R.'s planner: A* over actions

F.E.A.R. (Monolith, 2005) shipped a GOAP planner in place of a large hand-authored state machine; its character state machine has only three states. Jeff Orkin's GDC 2006 paper[3] describes the system: each NPC has an Action Set, actions carry preconditions, effects, and a cost, and the AI runs A* over a graph whose nodes are world states and whose edges are actions, searching for the lowest-cost action sequence that satisfies the current goal. The same A* code also plans paths through the navmesh. Action Sets are authored per character type: given the same goals, the soldier patrols and opens fire, the assassin runs cloaked, clings to walls, and lunges into melee, and the rat only patrols because it has no attack actions. When an action fails, the character replans with what it learned; in the paper's example, a character whose door the player holds shut tries to open it, replans to kick it, and replans again to dive through a window. The state graph is implicit; A* generates it as it expands.
3 · Asset cooking and the SCC report

An engine's asset cooker walks a dependency DAG: a character references a skeletal mesh and an animation graph, both reference a skeleton, the mesh references its materials, and each material references shaders and textures. Cooking visits the DAG bottom-up (reverse topological order: each dependency is baked before each dependent). When a content author accidentally introduces a cycle (say, a material and a material function that reference each other), an SCC pass (§9) turns the failure into a report naming the members: every SCC with more than one vertex is a cycle group, and Tarjan's algorithm emits each group as one pop sequence off its stack. Printing an ordered loop such as "circular dependency: M_RustyBarrel → MF_RustNoise → M_RustyBarrel" then takes one short DFS inside the component.
4 · Scene-graph traversal: flat preorder beats recursive

The fast scene-graph layout stores the hierarchy in a flat array ordered so every parent comes before its children: preorder, or breadth-first (level) order, which also keeps siblings contiguous. Each entry holds its parent's index. Computing world transforms is a single sequential pass over the array: each entity's world transform is its local transform composed with its parent's world transform, and the parent has already been processed because of the ordering. The pass needs no queue, no stack, and no pointer chase. The asymptotic class is the same as recursive DFS; the constant factor drops because the per-node DRAM miss is gone. Unity's Entities package takes the ECS route to the same data: transforms are plain components (LocalTransform in, LocalToWorld out), and a dedicated system recomputes LocalToWorld from the hierarchy each update[28].
5 · Navmesh A* in CryEngine, Unreal, and Detour

CryEngine documents its pathfinder as A* over the triangles of its navigation mesh, with the distance to the destination as the heuristic, time-sliced so path requests queue up and complete over several frames instead of spiking one[29]. Unreal's navmesh is a RecastNavMesh actor[30], and Recast's README lists both Unreal and Unity among the engines it powers[2]. Detour's own findPath is a compact A* worth reading: node positions at portal-edge midpoints, costs as distance times area cost, the 0.999-scaled straight-line heuristic, and closed nodes reopened when a cheaper route turns up[31].
